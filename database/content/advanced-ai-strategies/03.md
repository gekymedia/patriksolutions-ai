# Module 3 — Building AI Assistants & Agents

**Estimated time:** ~100 minutes · **Lessons:** 5

## Learning objectives
By the end of this module you will be able to:
- Explain the difference between a chatbot, a custom assistant, and an agent.
- Build your own custom AI assistant with no code (system instructions + knowledge).

- Understand what agents do, where they shine, and where they're risky.

**No-code core.** One **⌨️ Optional coding** sidebar for those who want to build an agent in code.

## Lesson 3.1 — Chatbot vs. assistant vs. agent (clear definitions)

These words get thrown around. Here's the honest distinction:

- **Chatbot / plain chat:** you type, it replies. Each chat starts fresh. (What you've used so far.)
- **Custom assistant:** a chat **pre-loaded with instructions and knowledge** for a specific job. It already knows its role, your rules, and reference material — so you (or others) just use it, no re-prompting. Examples: a "Customer Reply Assistant" that always answers in your brand voice, or a "Proposal Writer" that knows your services and pricing.
- **Agent:** an AI that can **take actions and make decisions in a loop to reach a goal** — not just reply, but *do*: search the web, run a calculation, call another tool, check the result, and try again. An agent is "assistant + the ability to act + the ability to decide the next step."

**Simple analogy:**
- Chatbot = a knowledgeable person answering questions.
- Assistant = that person, briefed on your business, with your files on their desk.
- Agent = that person who can also pick up the phone, look things up, and complete the task for you — deciding each next step themselves.

Most business value today comes from **custom assistants** (reliable, controllable). Agents are powerful and improving fast, but need more guardrails. We'll build an assistant for real, and understand agents clearly.

## Lesson 3.2 — Build a custom assistant with NO code

All the major tools let you create a saved, reusable assistant without coding. Names differ (and change), but the idea is identical:

| Tool | Feature (names change) | Free? |
|---|---|---|
| ChatGPT | "GPTs" / custom GPTs; "Projects" | Creating/using GPTs may require a paid plan; Projects vary |
| Claude | "Projects" (custom instructions + knowledge) | Available on free/paid tiers (limits vary) |
| Google Gemini | "Gems" (custom assistants) | Free tier available |
| Microsoft Copilot | "Agents"/custom Copilots | Varies by plan |

> Features and plan requirements change often — check the tool's current docs. **Free no-code fallback** if your tool's custom-assistant feature is paywalled: create a **"starter prompt" document** (your full system instructions + reference info) and paste it at the top of a new chat each time. Not as smooth, but it's free and works anywhere.

**What you give a custom assistant (three things):**
1. **System instructions** — who it is, how it behaves, its rules (Lesson 3.3).
2. **Knowledge** — reference files it should use (your FAQ, price list, brand guide, SOPs) — covered more in Module 4.
3. **A name + starter prompts** — so anyone can use it ("Click me and ask for a quote").

**Build-it steps (same everywhere):** open the "create assistant/GPT/Gem/Project" option → paste your system instructions → upload any reference files → add example starter prompts → save → test. That's a real AI tool you built, usable by you or your team, no code.

## Lesson 3.3 — Writing great system instructions

System instructions are the "job description + rulebook" that make an assistant reliable. A strong set covers:

```
IDENTITY: You are [name], the [role] for [business]. 
PURPOSE: Your job is to [the one main thing].
AUDIENCE: You help [who].
VOICE: [tone, style, do's and don'ts — paste your Voice note].
RULES:
- Only answer within [scope]. If asked outside it, say so and redirect.
- Use the knowledge files for facts; if unsure, say "I'm not sure" rather than guessing.
- Never share [sensitive things]. Never promise [what you can't deliver].
- For [high-stakes situations], tell the user a human will follow up.
WORKFLOW: When someone asks for X, do [steps]. Always [format].
IF UNSURE: ask a clarifying question instead of guessing.
```

**Example — "Bright Home Care Reply Assistant":**
```
IDENTITY: You are "CareReply," the customer-message assistant for Bright Home Care.
PURPOSE: Draft warm, accurate replies to families inquiring about care.
VOICE: compassionate, reassuring, plain English, never pushy or salesy.
RULES:
- Use only the info in the knowledge files (services, hours, pricing ranges).
- Never give medical advice. Never quote an exact price for a specific person — give ranges and invite a free assessment.
- For urgent safety concerns, say a care manager will call right away and flag it for a human.
IF UNSURE: ask one clarifying question.
OUTPUT: a ready-to-send reply under 120 words, plus a one-line note to staff of anything to double-check.
```

Notice how much safer and more consistent this is than a blank chat. **The instructions are where you encode judgment and guardrails** — this is the real craft of building assistants.

## Lesson 3.4 — What agents do (and the guardrails they need)

An **agent** goes beyond replying — it pursues a goal by taking actions in a loop: *think → act (use a tool) → observe the result → decide the next action → repeat → finish.*

**Where agents shine:**
- Tasks with several lookups/actions: "research these 10 companies and build a comparison table."
- Multi-tool jobs: "check the calendar, find a slot, draft the invite, and send it."
- Things too fiddly for a single reply but too repetitive to babysit.

**Where agents are risky (build guardrails):**
- **Taking real actions** (sending emails, spending money, changing data) — a wrong decision has real consequences. Require **approval before irreversible actions**.
- **Getting stuck in loops** or going off-task — set **limits** (max steps, a budget, a timeout).
- **Compounding errors** — one bad step feeds the next. Add **checks between actions**.
- **Security** — if an agent can read untrusted content (web pages, emails), that content can try to trick it ("prompt injection"). Never let an agent act on instructions found in data as if they were your orders (more in Module 7).

**The practical stance for now:** build **custom assistants** for most real work (reliable, controllable). Use **agent features** where they clearly save time, but keep a human approving anything irreversible. Agents are the frontier — powerful, worth understanding, used with care.

> **⌨️ Optional coding sidebar — building an agent in code**
> Developers build agents by giving a model "tools" (functions it can call — search, send email, query a database) and letting it loop: the model decides which tool to call, your code runs it, feeds the result back, and repeats until done. Frameworks exist (e.g., the OpenAI/Anthropic SDKs' tool-use, LangGraph, etc.). Core safety rules are the same as above: limit steps, require approval for irreversible actions, validate between steps, and never trust instructions embedded in data. **Not required to pass** — your no-code assistant capstone is fully valid.

## Lesson 3.5 — Testing your assistant before you trust it

A custom assistant is only as good as its testing. Before you (or your team) rely on it:

1. **Write 5–10 realistic test inputs**, including tricky ones (a vague question, an out-of-scope request, a sensitive case).
2. **Run each** and check: Did it follow its rules? Stay in voice? Refuse what it should refuse? Avoid inventing facts?
3. **Fix the instructions** where it slipped (add a rule, clarify scope) and re-test.
4. **Test the edges:** try to get it to break a rule (quote an exact price, give medical advice). If it does, tighten the instructions.
5. **Document** what it's good at and its known limits.

This test-and-tighten loop (expanded in Module 6) is what turns a neat demo into something dependable.

## 🎬 Instructor demonstration script
1. **Define the three** on screen (chatbot/assistant/agent) with the "person" analogy.
2. **Build a custom assistant live** (use Gemini Gems or Claude Projects if free): paste system instructions, add a small knowledge file (FAQ), add starter prompts, save.
3. **Use it:** ask a normal question (great), an out-of-scope question (it redirects), and a "quote me an exact price" trap (it gives a range + invites assessment). "The instructions did that."
4. **Show an agent concept** (e.g., a tool's browsing/agent mode doing a multi-step research task), then stop and say: "Powerful — but notice it's taking actions. For anything irreversible, keep a human approving."
5. **Run 3 test inputs** and tighten one rule live.

## 🛠️ Hands-on exercise (35 min)
1. Choose a job for an assistant (reply drafting, proposal writing, FAQ answering).
2. Write **system instructions** (identity, purpose, voice, rules, guardrails, output).
3. **Build it** in your tool's custom-assistant feature (or the free starter-prompt fallback). Add one small knowledge file.
4. **Test** with 5 inputs including one out-of-scope and one sensitive. Tighten the rules where it slips.
5. Write a 3-line note: what it's good at, its limits, where a human must stay involved.

**You're done when** you have a working custom assistant that passes your 5 tests (including refusing an out-of-scope/sensitive request).

## ✅ Quiz (with answers & explanations)

**Q1. The key difference between an assistant and an agent is…**
A) Price
B) An agent can take actions and decide next steps in a loop, not just reply
C) The color of the icon
D) Agents are older technology
**Answer: B.** Agents *act and decide*; assistants reply (pre-briefed).

**Q2. System instructions are…**
A) The user's question
B) The assistant's job description + rules that shape how it always behaves
C) A pricing tier
D) The output
**Answer: B.** They encode role, voice, rules, and guardrails.

**Q3. If your tool's custom-assistant feature is paywalled, a free alternative is…**
A) Give up
B) Keep a "starter prompt" doc and paste it at the top of each new chat
C) Switch careers
D) Only use voice
**Answer: B.** The starter-prompt doc replicates it for free.

**Q4. For an agent that can take real actions, a core guardrail is…**
A) Let it do anything for speed
B) Require human approval before irreversible actions; limit steps; validate between steps
C) Never test it
D) Hide it from users
**Answer: B.** Approval for irreversible actions + limits + checks.

**Q5. True or false: You should trust a new custom assistant in production before testing it with tricky and out-of-scope inputs.**
**Answer: False.** Test-and-tighten (including edge cases) first.
